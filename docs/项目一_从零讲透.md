# 项目一：文档知识库问答（RAG 混合检索）—— 从零讲透

> 读者假设：没做过 RAG、没写过检索 SQL、只知道「大模型能回答问题」。
> 目标：读完后你能把这套东西讲给别人听，也能接住追问。

---

## 1. 一句话说清这个项目

**你做的是一个「开卷考试」系统**：给它一批文档，你问一句话，它先翻书找到最相关的几段，再照着这几页回答你，并且告诉你答案在第几页。

翻书那一步叫**检索（retrieval）**，照书答题那一步叫**生成（generation）**。合起来叫 **RAG**（Retrieval-Augmented Generation，检索增强生成）。

**这个项目你只做了「翻书」那一半，而且把它做准了。** 这句话很重要——面试时别把它说成「我做了个 AI 问答机器人」，要说「我调的是检索，不是模型」。

---

## 2. 为什么需要 RAG（不讲这个，后面全是空中楼阁）

大模型有两个天生毛病：

1. **它不知道你的私有文档**。公司 300 页规章制度、你毕设的设计文档，它训练时没见过。
2. **它不知道就会编**。你问「报销上限多少」，它不会说「我不知道」，它会给你一个听起来很合理的数字。

解决「不知道你的文档」有两条路：

| 做法 | 本质 | 代价 |
|---|---|---|
| 微调（fine-tune） | 把文档「烧」进模型权重 | 贵、慢、文档一改就得重训、还容易把模型教傻 |
| **RAG** | 文档不动，回答时现场查 | 便宜、文档随时能改、能给出来源 |

工业界默认选 RAG。**RAG 的效果上限，几乎完全由「翻书翻得准不准」决定**——翻错页，再强的模型也只能照着错的页答，而且答得很自信。

这就是为什么「检索调优」是个正经技能，也是你这个项目的立身之本。

## 4. 文档怎么变成「能查的东西」

### 4.1 切分（chunking）

一整篇 5000 字的文档没法直接检索——你问一句，它只能给你「整篇」，等于没给。所以要切成段。

| 切法 | 后果 |
|---|---|
| 按固定字数硬切 | 一句话被切成两半，两半都检索不到 |
| 按段落 / 换行切 | 好一点，但长段落还是一大坨 |
| **按标题层级下钻** | 每段自带「它在哪一章哪一节」，命中率高 |

**必须说清：MaxKB 的智能分段本来就支持按 Markdown 标题逐级下钻**（最多 6 级，每段上限 4096 字符）。所以「改造分块」不是你的功劳，别说成你做的。你真正加的是：**表格整表保留表头 + 每段带 文件名:行号**，这样引用能定位回原文。

### 4.2 向量化（embedding）

把一段文字丢给 embedding 模型，出来 768 个浮点数。**语义相近的两段文字，它们的向量在空间里也靠得近。** 就这样，别被「高维空间」吓到。

### 4.3 入库

pgvector 在 PostgreSQL 里加了一种新类型：vector(768)。存进去之后可以用 <=> 算子算**余弦距离**：

- 返回 0 = 两个向量同向（语义几乎一样）
- 返回 1 = 垂直（不相关）
- 所以 **1 - 距离 = 余弦相似度**，落在 0~1，越大越像

### 4.4 353 段为什么有 693 条向量

因为 MaxKB 会给每个段落**自动生成几个「关联问题」**，每个问题也单独存一条向量。这样用户问「报销怎么走」能对上原文「费用报销流程」。

**副作用（重要）**：同一段会在结果里占多个名次。做融合时必须**按段落去重**，否则一段话能把 Top-5 占满。

## 5. 两路检索：它们各自瞎在哪

### 5.1 向量检索（语义路）

问「报销上限多少钱」，能找到写着「费用额度不得超过 X 元」的段落——**字面上一个词都不一样，意思对上了**。这是向量的本事。

它瞎在**具体、罕见、字面的东西**上：

- 问「EE-203 怎么配置」——这种编号在向量里几乎没有语义，会被「平均」成一团模糊
- 问某个函数名、错误码、产品型号，同理

### 5.2 全文检索（关键词路）

PostgreSQL 自带：把段落切成词（tsvector），查询也切成词（tsquery），按**词命中 + 词频 + 词距离**打分（ts_rank_cd）。

它瞎在**换个说法就找不到**：问「报销」找不到写着「费用核销」的段落。

### 5.3 所以要混合（hybrid）

一路管「意思像」，一路管「字面对」。**两路的错误不重叠**，合起来才稳。这就是混合检索的全部动机。

## 6. 原版 MaxKB 怎么合的（重点，逐句讲）

原始 SQL 在 apps/knowledge/sql/blend_search.sql，27 行，骨架：

~~~sql
WITH vector_top AS (
    SELECT id, paragraph_id, (embedding::vector(%s) <=> %s) AS distance
    FROM embedding ${embedding_query}        -- 带 knowledge_id 过滤的 WHERE
    ORDER BY (embedding::vector(%s) <=> %s)
    LIMIT LEAST(%s * 10, 500)                 -- 关键：先砍到最多 500 条
)
SELECT DISTINCT ON (paragraph_id) ...
    (1 - distance + COALESCE(ts_rank_cd(search_vector,
        websearch_to_tsquery('simple', %s), 32), 0)) AS comprehensive_score
FROM vector_top JOIN embedding e ON e.id = vector_top.id
ORDER BY paragraph_id, comprehensive_score DESC
...
WHERE comprehensive_score > %s
ORDER BY comprehensive_score DESC
LIMIT %s
~~~

翻成人话：

1. **先用向量找最像的 500 段**（LIMIT LEAST(top_number*10, 500)）
2. **在这 500 段里，再给每段加一个关键词分**（ts_rank_cd）
3. 两者相加当总分，排序取前 K

### 6.1 缺陷一：候选池是死的（真正的病根）

关键词分**只能给已经进了池子的段落加分**。如果一段话字面完全命中、但语义不像（编号、型号、错误码），它**根本不在那 500 条里**，关键词再准也加不到分。

这叫「**召回上限被另一路锁死**」。你实测的旁证很硬：池子从 50 放大到 500，命中率**反而从 75% 掉到 41.7%**——说明瓶颈不是「池子不够大」，而是「池子由谁决定」。

### 6.2 缺陷二：两项直接相加，但量级不对等

- 余弦相似度：中文 embedding 上**普遍 0.8 以上**（两句话只要都是通顺中文，就不会太低）
- ts_rank_cd(..., 32)：数字 32 是归一化开关，含义是 rank/(rank+1)，**恒小于 1**，弱命中时接近 0

两项都在 [0,1) 里，看起来「量纲一致、可以相加」。**但分布差一个量级**：0.85+0.05 和 0.93+0.00 比，前者还是输。结果——**关键词项只够做同分微调，基本改不了排序**。

> 自己量一遍（这一步最能证明你真读过源码）：
>
> ~~~sql
> -- 余弦：随便取几行看分布
> SELECT round((1 - (embedding <=> (SELECT embedding FROM embedding LIMIT 1)))::numeric, 4)
>   FROM embedding LIMIT 5;
> -- 全文分：同一个词
> SELECT round(ts_rank_cd(search_vector, websearch_to_tsquery('simple','打招呼'), 32)::numeric, 4)
>   FROM embedding WHERE search_vector @@ websearch_to_tsquery('simple','打招呼') LIMIT 5;
> ~~~
>
> 会看到余弦一片 0.8~0.99，全文分一片 0.0x~0.3。

## 7. 你改成了什么：RRF 名次融合

### 7.1 RRF 是什么

**Reciprocal Rank Fusion（倒数名次融合）**，一句话：**不看分数，只看名次。**

~~~
score(文档) = Σ  1 / (k + rank)        k = 60，rank = 它在某一路里的名次（从 1 开始）
~~~

### 7.2 手算一遍（面试被问就讲这个）

两路各召回 20 条，某篇文档：

| | 向量路名次 | 全文路名次 | RRF 分 |
|---|---|---|---|
| 文档 A | 3 | 7 | 1/63 + 1/67 = **0.0308** |
| 文档 B | 1 | 未命中 | 1/61 = **0.0164** |

**A 赢了 B**，尽管 B 在向量路排第一。因为 A **被两路同时认可**——这正是混合检索要的「投票」效果。

### 7.3 为什么用它（三条，每条都是答辩素材）

1. **免疫量纲**：只用名次，余弦和 ts_rank_cd 谁大谁小都无所谓。
2. **免调权重**：cos*0.7 + bm25*0.3 这种权重得随语料重调，RRF 一个 k 通吃。
3. **k=60 的作用**：压低头部绝对优势。k 越小第 1 名越霸，k 越大名次差异被抹平。实测 20/60/100 差异在 ±1.5 个点内。

### 7.4 关键发现：融合的「粒度」决定成败

你试了四种粒度，结果天差地别：

| 做法 | Top-5 |
|---|---|
| 原版 blend（池内加全文分） | 13/24 = 54.2% |
| SQL 内按段落融合 RRF | 12/24 = 50.0% |
| SQL 内按文档聚合 RRF | 9/24 = 37.5% |
| 离线、按段落 id 融合两路 top-20 | 14/24 = 58.3% |
| **离线、按文档名次融合两路 top-20** | **20/24 = 83.3%** |

为什么「文档级」这么重要：同一篇文档里有多个段落同时命中，**段落级融合会被「这篇文档有多少段」带偏**——段多就等于票多。按文档取「它在每路里最好的那个名次」，才是公平比较。

**这一段是整个简历里最硬的东西**：你不仅做出了 83.3%，还知道「塞进 SQL 会掉到 50%」，并能解释为什么。

## 8. 评测怎么做（没有这个，83% 就是空口）

### 8.1 标注集

- **24 道域内题**：每题人工标「标准答案在哪个文件」
- **8 道域外题**（问「红烧肉怎么做」这种库里没有的）：测**拒答**
- 题面故意混了典型失败类型：编号型（EE-203）、专名型、口语转述型、跨文档综合型

### 8.2 协议（必须一次说清，否则数字会被质疑）

> 每题各模式取 top_number=20 → 按**文档名**去重 → 取前 5 篇 → **标准答案所在文件出现在这 5 篇里就算命中**。

这就是「**文档级 Top-5**」的含义。换成段落级 Top-5 数字会低很多，别混着说。

### 8.3 结果

| 模式 | Top-5 命中 |
|---|---|
| 纯向量 | 12/24 = 50.0% |
| 纯全文 | 12/24 = 50.0% |
| 原版混合（blend） | 13/24 = 54.2% |
| **RRF 文档级融合** | **20/24 = 83.3%** |

**单路都只有 50%，融合才 83%**——这句话是「混合检索有价值」的直接证据，务必背下来。

### 8.4 稳健性（防止被说「调参调出来的」）

| 变体 | Top-5 |
|---|---|
| RRF，两路各取 Top-10 | 75.0% |
| 原版 blend，请求 top_number=5（池 50） | 75.0% |
| 原版 blend，top_number=50（池 500） | 41.7% |

### 8.5 拒答

域外 8 题、阈值取余弦 0.5：**7/8 正确拒答**（「这个话题我知识库里没有」），域内 0 误拒。

阈值怎么定的标准答法：**在标注集上扫参数，取「域内多保留、域外多拒掉」的平衡点，落在 0.5。**

## 9. 你踩过的坑（讲这些最像「真做过」）

1. **一条 SQL 换不掉**：SQL 里必须**恰好 8 个 %s**，因为 Python 侧 BlendSearch.handle 固定按顺序传 8 个参数。多加一个 LIMIT %s 就报 the query has 10 placeholders but 9 parameters were passed。
2. **注释里的 % 也会被当占位符**：文件首行写了「-- % MaxKB ...」，直接报 incomplete placeholder: '%'。这坑只有真跑过才会遇到。
3. **段落去重**：一段多向量，不去重会让同一段占满 Top-5。
4. **MaxKB 的 API 前缀是 /admin/api/**，不是 /api/；文档上传是两步（先 split 再 document），直接 POST 只建空壳。
5. **容器重建会丢改动**：docker cp 进去改的 SQL，容器一重建就没了，得 bind mount。
6. **库里的用户是 root**，没有 postgres 角色，连库要 -U root。

| 能做 | 不能做 |

## 11. 术语卡（10 个词，能用人话解释就够）

| 术语 | 人话 |
|---|---|
| RAG | 先查资料再回答，防止模型瞎编 |
| chunking（切分） | 把长文档切成能独立检索的段 |
| embedding（向量化） | 把一句话变成 768 个数字，语义近则数字近 |
| 向量检索 | 按「意思像」找，同义改写也能命中 |
| 全文检索 | 按「字面命中」找，编号、错误码靠它 |
| 混合检索（hybrid） | 两路都跑，结果合并 |
| RRF | 只看名次合并多路结果，Σ1/(60+rank) |
| 候选池（recall pool） | 进入排序环节的候选集合，池子由谁决定就决定了上限 |
| Top-K 命中率 | 前 K 条里有没有标准答案 |
| 拒答 | 知识库里没有就明说，别硬编 |

## 12. 60 秒完整讲述（背下来，面试第一问就用）

> 这个项目基于 MaxKB 做文档知识库问答，我改的是检索层。
> 它的混合检索先把候选池砍到向量 Top-500，再在池子里把余弦相似度和全文分相加。这有两个问题：一是纯字面命中（编号、型号）根本进不了池子；二是两项分数量级差一个档，相加基本等于只看向量。
> 我做了两件事：两路各自独立召回；用 RRF 按名次融合，在文档维度取每篇的最好名次再合并。
> 评测是我自己标的 24 道题加 8 道域外题。原版混合检索文档级 Top-5 是 54.2%，改完是 83.3%，而纯向量和纯全文各只有 50%。
> 我也试过直接把 RRF 写进那条 SQL，结果段落级只有 50%、按文档聚合只有 37.5%，比原版还低——所以瓶颈在候选池和融合粒度，不在公式。域外 8 题拒答 7 题。
