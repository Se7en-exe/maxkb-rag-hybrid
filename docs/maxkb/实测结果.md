# MaxKB v2.10.8 真机实测：混合检索 vs RRF 名次融合

> 环境：Docker Desktop 29.9.3 + WSL 3.0.5，镜像 1panel/maxkb:v2.10.8-lts，
> 容器内 PostgreSQL 17.11 + pgvector，embedding = shibing624/text2vec-base-chinese（768 维）。
> 语料：corpus/docs 38 个文件（md/docx/pdf），切分后 **353 段 / 693 条向量**。
> 标注：eval/cases_docs.py 的 24 条问答（人工标注「正确答案在哪个文件」）+ 8 条域外问题。

## 一、接入方式（踩过的坑）

| 事项 | 结论 |
|---|---|
| 管理端 API 前缀 | `/admin/api/`（不是 `/api/`）。来源：`apps/maxkb/urls/web.py` 的 `admin_api_prefix = CONFIG.get_admin_path()[1:] + '/api/'`，容器 env `MAXKB_ADMIN_PATH=/admin` |
| 认证头 | `Authorization: Bearer <token>`。裸 token 会被判「非法用户」 |
| 登录 | `POST /admin/api/user/login`，`admin / <你的密码>` |
| workspace_id | `default`（来自 `/admin/api/user/profile` 的 role `WORKSPACE_MANAGE:/WORKSPACE/default`） |
| 建知识库 | `POST /admin/api/workspace/default/knowledge/base`（**不是** `/knowledge`，后者只允许 GET） |
| 传文档 | 两步：`POST .../document/split` 上传文件拿切分结果 → `POST .../document` 提交 `{name, paragraphs}`。直接 POST `/document` 只会建一条空记录（char_length=0、段落 0） |
| 命中测试 | `POST .../knowledge/{kid}/hit_test`，`{query_text, top_number, similarity, search_mode}`，search_mode ∈ `embedding | keywords | blend` |
| 数据库 | `psql -h 127.0.0.1 -U root -d maxkb`（用户 root，**没有** postgres 角色），密码 `MAXKB_DB_PASSWORD` |

## 二、主实验：同一标注集、同一协议下的四路对比

**协议（关键，面试必须能说清）**：每个模式请求 `top_number=20`，返回 20 个段落，
按 `document_name` 去重后取**前 5 个文档**；命中 = 答案文件的文件名出现在这 5 个里。

| 模式 | Top-5 命中 | 说明 |
|---|---|---|
| 纯向量（embedding） | **12/24 = 50.0%** | MaxKB 内建向量通道 |
| 纯全文（keywords） | **12/24 = 50.0%** | `keywords_search.sql`，ts_rank_cd |
| **原版混合（blend）** | **13/24 = 54.2%** | `blend_search.sql`：向量池 Top-(k*10, ≤500) 内按 `(1-distance)+ts_rank_cd` 相加 |
| **RRF 名次融合** | **20/24 = 83.3%** | 两路各取 Top-20 名次，`Σ1/(60+rank)` |

**+29.1 个百分点**，且路径是纯 SQL 级替换（不动 Python 调用方）。

### 为什么涨这么多：逐题名次（节选）

| 问题 | 向量 | 全文 | 原版 blend | RRF |
|---|---|---|---|---|
| 打招呼第一句话怎么写 | 12 | 3 | 13 | **2** |
| 简历优化服务值不值得买 | 9 | 8 | 7 | **4** |
| 三条改造方向里哪条最适合一周做完 | 7 | 11 | 13 | **3** |
| 投递转化率低是什么原因 | 12 | 6 | 9 | **4** |
| 三个开源方向分别选哪个项目 | 5 | 6 | 7 | **3** |
| 项目二推荐用什么技术栈 | 11 | 6 | 6 | **5** |
| 改了别人的代码怎么证明是我改的 | 8 | 7 | 5 | **4** |

规律：**单路排名 6~13 名的文档，两路同时排在中段时被 RRF 顶到前 5**。
原版是「余弦相似度 + 全文分数」直接相加，两项都在 [0,1)（32 号归一化把全文分压成 rank/(rank+1)），
但分布差一个档：余弦普遍 0.8 以上、全文分多在 0.1 以下，中段命中的文档靠这点分顶不过余弦本身就高的头部；
RRF 只看名次，两路都排中段 = 双份 1/(60+rank)，自然抬上来。

## 三、稳健性检验（防「调参调出来的」质疑）

| 变体 | Top-5 |
|---|---|
| RRF，两路各取 Top-10（候选减半） | 18/24 = **75.0%** |
| RRF，两路各取 Top-20 | 20/24 = **83.3%** |
| 原版 blend，但请求 `top_number=5`（向量池缩到 50） | 18/24 = 75.0% |
| 原版 blend 请求 `top_number=50`（向量池扩到 500 上限） | 10/24 = 41.7% |

两个结论：
1. **候选减半 RRF 仍 75%**，说明收益不是靠堆候选数。
2. **原版把向量池从 50 放大到 500，命中反而从 75% 掉到 41.7%** —— 池子越大，
   噪声段落越多，`(1-distance)` 的加性优势被稀释，真正想找的那段被挤出前 5。
   这条是「瓶颈在候选池与打分方式，不在模型」最硬的证据。

## 四、拒答

8 条域外问题（红烧肉、写诗、考研、马甲线…），blend + `similarity=0.5`：**7/8 返回空**（正确拒答），
1 条漏拒。域内 24 题在该阈值下无一条被误拒（0 误拒）。

## 五、RRF SQL 真机验证

`docs/maxkb/blend_search_rrf.sql` 已在本机 PostgreSQL 17.11 + pgvector 上跑通：

- 空表执行：返回 0 行，无语法/类型错误（8 个占位符与 `exec_params` 逐位对齐）
- 真实向量执行：取库内一条 768 维向量当查询向量、`websearch_to_tsquery('simple','简历')`，
  返回 5 行，`rrf_score` 量级 0.035~0.046（= 1/61+1/62+1/63 量级），与 `csb.retrieval.rrf_fuse` 实算一致

## 六、一句话版本（面试用）

> MaxKB v2 的混合检索是「向量池内加全文分」：候选先被向量 Top500 卡死，字面命中进不来，
> 而且两个不同量纲的分数直接相加。我在真机上用同一份 24 题标注集量过：纯向量 50%、纯全文 50%、
> 原版混合 54.2%；把两路名次用 RRF 融合、只替换那一条 SQL，Top-5 到 83.3%。
> 关键证据是原版把向量池从 50 扩到 500、命中反而从 75% 掉到 41.7% —— 说明瓶颈在候选池和打分，
> 不在 embedding 模型。

## 七、重要更正：单条 SQL 替换做不到 83.3%（2026-11-15 实测）

把 RRF 直接写进 `blend_search.sql` 装进运行中的容器，实测结果**不如原版**：

| 版本 | Top-5（同协议：top_number=20，按文档去重取前 5） |
|---|---|
| 原版 blend（向量池内加全文分） | 13/24 = **54.2%** |
| RRF，段落级融合（一条 SQL 内，按 paragraph_id） | 12/24 = 50.0% |
| RRF，文档级融合（SQL 内按 document_id 聚合） | 9/24 = 37.5% |
| RRF，离线按**段落 id** 融合两路 top-20 | 14/24 = 58.3% |
| RRF，离线按**文档名次**融合两路 top-20 | 20/24 = **83.3%** |

结论：**83.3% 的来源不是 RRF 公式本身，而是「文档级 + 每路只取前 20」这个融合协议。**
- 段落级融合只比原版好 4 个点（58.3% vs 54.2%）
- 文档级融合跳到 83.3%，因为它是「这篇文档在两路里各排第几」的投票，段落数量不再影响分数

所以简历/面试里说「RRF 83.3%」必须带上限定：**文档级名次融合、每路取前 20**。
若被要求「现场把 SQL 改了我看」，改不出来 —— 正确说法是「融合做在检索层（改 `pg_vector.py` 的 BlendSearch），不是一条 SQL」。

容器已恢复原版（`blend_search.sql` 672 字节，备份 `blend_search.sql.orig`），实测回到 54.2%。
