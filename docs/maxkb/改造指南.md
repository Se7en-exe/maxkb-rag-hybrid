# MaxKB 混合检索改造：RRF 版（可直接替换）

> 上游版本：**v2.10.8-lts**（2026-10-22 发布）
> 替换文件：`apps/knowledge/sql/blend_search.sql`
> Python 代码：**一行都不用改**

---

## 一、原版在做什么（面试时就讲这一段）

打开 `apps/knowledge/sql/blend_search.sql`，全文只有 20 行：

```sql
WITH vector_top AS (
    SELECT id, paragraph_id, (embedding::vector(%s) <=> %s) AS distance
    FROM embedding ${embedding_query}
    ORDER BY (embedding::vector(%s) <=> %s)
    LIMIT LEAST(%s * 10, 500)
)
SELECT paragraph_id, comprehensive_score, comprehensive_score AS similarity
FROM (
    SELECT DISTINCT ON (vc.paragraph_id) vc.paragraph_id,
        (1 - vc.distance + COALESCE(ts_rank_cd(e.search_vector,
             websearch_to_tsquery('simple', %s), 32), 0)) AS comprehensive_score
    FROM vector_top vc JOIN embedding e ON e.id = vc.id
    ORDER BY vc.paragraph_id, comprehensive_score DESC
) sub
WHERE comprehensive_score > %s
ORDER BY comprehensive_score DESC
LIMIT %s
```

**两个可攻击的点：**

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | 候选池只从向量通道来 | `LIMIT LEAST(%s * 10, 500)` 作用在 `ORDER BY 向量距离` 上 | 纯字面命中、语义不相似的段落**永远进不了池子** |
| 2 | 两项直接相加，但量级不对等 | `(1 - distance) + ts_rank_cd(...,32)` | 32 号归一化后全文分 = rank/(rank+1) ∈ [0,1)；余弦普遍 0.8+、全文分多在 0.1 以下 → 相加几乎等于只看向量分，关键词项只够做同分微调 |

调用方在 `apps/knowledge/vector/pg_vector.py` 第 308-343 行的 `class BlendSearch.handle`，
它传 8 个参数（`exec_params` 列表），最后一个是 `top_number`。

## 二、改成什么

同目录的 `blend_search_rrf.sql`：

- **两路各自独立取候选**：向量 Top-N 和全文 Top-M 互不设门
- **RRF 融合**：score = Σ 1/(k + rank)，k = 60（Cormack 等 2009 原论文取值）
- **只用名次、不用分数** → 免疫量纲差异，不需要任何权重调参
- **阈值语义改写**：原版 similarity 是「综合分必须大于它」，但 RRF 分数是 0.016 量级，直接套会全滤光。改成开关：>= 0.5 要求两路都命中（交集），< 0.5 任一路命中即可（并集）

**占位符顺序严格对齐（8 个）**，WITH 子句的书写顺序就是绑定顺序：

| # | 参数 | 用途 |
|---|---|---|
| 1 | len(query_embedding) | vector_top 距离表达式 |
| 2 | json(query_embedding) | 同上 |
| 3 | len(query_embedding) | vector_top 的 ORDER BY |
| 4 | json(query_embedding) | 同上 |
| 5 | top_number | 向量候选池大小 |
| 6 | to_query(query_text) | 全文通道查询词 |
| 7 | similarity | 交集/并集开关 |
| 8 | top_number | 最终返回条数 |

> 排错提示：如果日志报 IndexError 或「参数数量不匹配」，一定是这里错位。
> 最稳的验证：先跑一次原版，把 exec_params 打印出来，再对着表核。

## 三、怎么验证（这是要写进简历的部分）

```bash
# 1) 备份原文件
cp apps/knowledge/sql/blend_search.sql apps/knowledge/sql/blend_search.sql.orig

# 2) 替换
cp /path/to/blend_search_rrf.sql apps/knowledge/sql/blend_search.sql

# 3) 重启容器
docker restart maxkb

# 4) 进 MaxKB 网页 -> 知识库 -> 命中测试
#    相似度设 0.3（走并集）跑一遍，再设 0.6（走交集）跑一遍
```

**对照实验设计（别只跑一次就宣称变好）：**

| 组别 | 配置 | 记录 |
|---|---|---|
| A · 原版 | 默认 blend_search.sql | 24 题 Top-5 命中率 |
| B · RRF 并集 | 本版，阈值 0.3 | 同上 |
| C · RRF 交集 | 本版，阈值 0.6 | 同上 |
| D · 纯向量 | UI 切「向量」 | 同上 |
| E · 纯全文 | UI 切「关键词」 | 同上 |

题目集用 `eval/cases_docs.py` 那 24 条，期望答案文件已标注。

**预期结果**（据自研复刻的实测外推）：

- 文档库这种段落长度均匀的语料：并集 ≈ 原版，RRF 甚至可能低 1-2 个点
- 代码库/表格密集、块长方差大的语料：并集明显优，RRF 与原版持平或略优

如果跑出来和预期不符，**不要改数字，改结论**。真正的收获是「知道什么时候不该换公式」。

## 四、面试时怎么说（三句）

> **第一句**：MaxKB v2 本身就有混合检索，我没重复造轮子，我是去读它的实现。

> **第二句**：它的候选池只从向量通道取 Top500，关键词只负责给池内候选加分。也就是说，
> 只要语义模型没把某段话捞上来，后面关键词再准也没用。我把候选池改成两路独立召回再用 RRF 合并。

> **第三句**（最值钱）：但我拿文档库做对照，发现换成 RRF 并没有变好，甚至低了一点。
> 原因是文档段落长度均匀，量纲问题不突出；代码块长度从 2 行到 400 行，量纲差距才被放大。
> **所以瓶颈在候选池，不在融合公式** —— 换公式救不了召回。
