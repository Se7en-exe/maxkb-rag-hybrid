你的项目是一个「开卷考试」系统

给它一批文档，你问一句，它先翻书找到最相关的几段，再照着这几页回答。翻书叫检索，答题叫生成，合起来叫 RAG。你只做了翻书那一半——而且是做准了的那一半。

MaxKB v2.10.8 PostgreSQL 17 + pgvector Docker 本地 embedding · 768 维 24 题自建标注集 54.2% → 83.3%

01一句话说清这个项目

整篇文档没法检索——你问一句，它只能把整篇丢给你，等于没给。所以要切段、要给每段算一个语义坐标、要能在几千段里挑出最像的五段。你改的就是最后那步「挑」。

面试定调的一句话

别说「我做了个 AI 问答机器人」。要说：「我调的是检索，不是模型。」这一句定完，后面所有追问都落在你能接住的框里。

RAG 的效果上限，几乎完全由「翻书翻得准不准」决定。翻错页，再强的模型也只能照着错的页答，而且答得很自信。这就是检索调优值得做成一个项目的原因。

02为什么非要 RAG，不能微调

大模型两个天生的毛病：不知道你的私有文档；不知道就编——你问报销上限，它不会说不知道，它会给你一个听起来很合理的数字（这叫幻觉）。

做法本质代价
微调 fine-tune把文档「烧」进模型权重贵、慢、文档一改就得重训、还容易把模型教傻
RAG文档不动，回答时现场查便宜、随时能改、能给出来源

工业界默认选 RAG。打个比方：微调是考前把整本书背下来，RAG 是允许带书进考场。

04文档怎么变成「能查的东西」

4.1 切分 chunking

切法后果
按固定字数硬切一句话被切成两半，两半都检索不到
按段落 / 换行切好一点，但长段落还是一大坨
按标题层级下钻每段自带「它在哪一章哪一节」，命中率高

必须诚实的一点

MaxKB 的智能分段本来就支持按 Markdown 标题逐级下钻（最多 6 级，每段上限 4096 字符）。所以「改造分块」不是你的功劳。你真正加的是：表格整表保留表头 + 每段带「文件名:行号」，让引用能定位回原文。

4.2 向量化 embedding

把一段文字丢给 embedding 模型，出来 768 个浮点数。语义相近的两段，向量在空间里也靠得近。就这样，别被「高维空间」吓到。

这里有个高频误会

embedding 模型 和 对话模型 是两个东西。本机只装了前者（text2vec-base-chinese），所以能查不能答——像雇了个会找书的图书管理员，但没雇会写作文的人。

4.3 入库与距离

pgvector 给 PostgreSQL 加了一个类型 vector(768)，和一个算子 <=> 算余弦距离：

  • 返回 0 = 同向（语义几乎一样）
  • 返回 1 = 垂直（不相关）
  • 所以 1 − 距离 = 余弦相似度，越大越像

4.4 353 段为什么有 693 条向量

MaxKB 会给每段自动生成几个「关联问题」，每个问题也单独存一条向量。这样问「报销怎么走」能对上原文「费用报销流程」。

副作用（融合时会要命）

同一段会在结果里占多个名次。做融合必须按段落去重，否则一段话能把 Top-5 全占满。

05两路检索：它们各自瞎在哪

向量检索（语义路）

问「报销上限多少钱」，能找到写着「费用额度不得超过 X 元」的段落——字面一个词都不一样，意思对上了。

瞎在：编号、型号、错误码。EE-203 在向量里几乎没有语义，会被「平均」成一团模糊。

全文检索（关键词路）

PostgreSQL 自带：段落切成词（tsvector），查询切成词（tsquery），按词命中 + 词频 + 词距离打分（ts_rank_cd）。

瞎在：换个说法就找不到。问「报销」找不到写着「费用核销」的段落。

两路的错误不重叠，所以合起来才稳。这就是混合检索存在的唯一理由——记住这一句，别的都是细节。

标注集里的真实例子

「打招呼第一句话怎么写」这道题：纯向量排第 12 名，纯全文排第 3 名。字面词对上了，语义没对上——这就是「两路互补」的现场证据。

06原版 MaxKB 怎么合的

文件在 apps/knowledge/sql/blend_search.sql，27 行。骨架：

WITH vector_top AS (
    SELECT id, paragraph_id, (embedding::vector(%s) <=> %s) AS distance
    FROM embedding ${embedding_query}          -- 带 knowledge_id 过滤的 WHERE
    ORDER BY (embedding::vector(%s) <=> %s)
    LIMIT LEAST(%s * 10, 500)                  -- ← 病根：先砍到最多 500 条
)
SELECT DISTINCT ON (paragraph_id) ...
    (1 - distance + COALESCE(ts_rank_cd(search_vector,
        websearch_to_tsquery('simple', %s), 32), 0)) AS comprehensive_score
FROM vector_top JOIN embedding e ON e.id = vector_top.id
ORDER BY paragraph_id, comprehensive_score DESC
WHERE comprehensive_score > %s
ORDER BY comprehensive_score DESC
LIMIT %s

翻成人话：① 先向量找最像的 500 段 → ② 在这 500 段里加关键词分 → ③ 相加排序取前 K。

6.1 缺陷一：候选池是死的（真正的病根）

关键词分只能给已经进了池子的段落加分。一段话字面完全命中、但语义不像（编号、型号），它根本不在那 500 条里，关键词再准也加不到分。这叫召回上限被另一路锁死。

旁证很硬

池子从 50 放大到 500，命中率反而从 75% 掉到 41.7%。说明瓶颈不是「池子不够大」，而是「池子由谁决定」。

6.2 缺陷二：两项直接相加，但量级不对等

先纠正一个常见错说法

别说「全文分没有上界」。ts_rank_cd(..., 32) 里的 32 是归一化开关，输出 = rank/(rank+1)，恒小于 1。读过源码的人一听这句就知道你在背。

真相是：两项都在 [0,1)，但分布差一个量级——中文 embedding 的余弦普遍 0.8 以上，全文分多在 0.1 以下。所以 0.85+0.05 和 0.93+0.00 比，前者还是输。关键词项只够做同分微调，基本改不了排序。

-- 自己量一遍，这一步最能证明你真读过源码
SELECT round((1 - (embedding <=> (SELECT embedding FROM embedding LIMIT 1)))::numeric, 4)
  FROM embedding LIMIT 5;
-- 余弦一片 0.8~0.99
SELECT round(ts_rank_cd(search_vector, websearch_to_tsquery('simple','打招呼'), 32)::numeric, 4)
  FROM embedding WHERE search_vector @@ websearch_to_tsquery('simple','打招呼') LIMIT 5;
-- 全文分一片 0.0x~0.3

07你改成了什么：RRF 名次融合

Reciprocal Rank Fusion（倒数名次融合），一句话：不看分数，只看名次。因为两路的分数根本不是一个尺子上的东西——一个是百分制，一个是五分制，别比分数，只比「他把他排第几」。

score(文档) = Σ  1 / (k + rank)      k = 60，rank = 它在某一路里的名次（从 1 开始）

7.1 动手算一次（面试被问就讲这个）

A 的分：0.0308
B 的分：0.0164
默认值就是面试要讲的那组

默认：A（向量 3 / 全文 7）、B（向量 1 / 未命中）。A 赢 B，尽管 B 在向量路排第一——因为 A 被两路同时认可。这就是「投票」效果，也是 RRF 的全部意义。

7.2 为什么用它（三条都是答辩素材）

  1. 免疫量纲：只用名次，余弦和 ts_rank_cd 谁大谁小都无所谓。
  2. 免调权重：cos*0.7 + bm25*0.3 这种权重得随语料重调，RRF 一个 k 通吃。
  3. k=60 的作用：压低头部绝对优势。k 越小第 1 名越霸，k 越大名次差异被抹平。实测 20 / 60 / 100 差异在 ±1.5 个点内。

7.3 关键发现：融合的「粒度」决定成败

原版 blend（池内加全文分）
54.2%
SQL 内按段落融合 RRF
50.0%
SQL 内按文档聚合 RRF
37.5%
离线 · 按段落 id 融合 top-20
58.3%
离线 · 按文档名次融合 top-20
83.3%

为什么「文档级」这么重要：一篇文档里有多个段落同时命中，段落级融合会被「这篇有多少段」带偏——段多就等于票多。按文档取「它在每路里最好的那个名次」，才是公平比较。

这是整份简历最硬的东西

你不仅做到了 83.3%，还知道把它塞进 SQL 会掉到 50%，并且能解释为什么。会做的人不少，知道边界的人不多。

08评测怎么做（没这个，83% 是空口）

8.1 标注集

  • 24 道域内题：每题人工标「标准答案在哪个文件」
  • 8 道域外题（「红烧肉怎么做」这种库里没有的）：测拒答
  • 题面故意混了典型失败类型：编号型、专名型、口语转述型、跨文档综合型

8.2 协议（必须一次说清，否则数字会被质疑）

每题各模式取 top_number=20 → 按文档名去重 → 取前 5 篇 → 标准答案所在文件出现在这 5 篇里就算命中。这就是「文档级 Top-5」。

09你踩过的六个坑（讲这些最像「真做过」）

  1. 一条 SQL 换不掉：必须恰好 8 个 %s，因为 Python 侧 BlendSearch.handle 固定按顺序传 8 个参数。多加一个 LIMIT %s 就报 the query has 10 placeholders but 9 parameters were passed。
  2. 注释里的 % 也算占位符：首行写「-- % MaxKB …」，直接 incomplete placeholder: '%'。这坑只有真跑过才会遇到。
  3. 段落去重：一段多向量，不去重会让同一段占满 Top-5。
  4. API 前缀是 /admin/api/，不是 /api/；上传文档是两步（先 split 再 document），直接 POST 只建空壳。
  5. 容器重建会丢改动：docker cp 进去改的 SQL，容器一重建就没了，得 bind mount。
  6. 库里用户是 root，没有 postgres 角色，连库要 -U root。

11术语卡（能用人话解释就够）

RAG先查资料再回答。开卷考试。防止模型瞎编。
检索 retrieval从几千段里挑出最相关的五段。翻书找页码。
生成 generation照着挑出来的几页写答案。本项目没接，所以只做检索。
幻觉模型不知道却编一个听起来很像的答案。
微调 fine-tune把文档「背」进模型脑子里。贵、慢、书一改就得重背。
prompt喂给模型的那段话。RAG 里一般长这样：根据以下资料回答……资料：{检索到的段落}。
chunking 切分把长文档切成能独立检索的小段。把一本书拆成一堆卡片。
段落 paragraph切分后的最小单位，就是一张卡片。
embedding 向量化把一句话变成一串数字。给每句话发一张语义身份证。
向量 vector那串数字，这里是 768 个小数。
768 维768 个数字组成的坐标，用来定位「这句话的意思在哪儿」。
embedding 模型干「句子→数字」这件事的模型。只会发身份证，不会说话。
pgvector给 PostgreSQL 装的插件，让它能存向量、算「像不像」。给档案柜加个按语义找的抽屉。
余弦相似度越接近 1 越像。1 − 距离 就是它。
余弦距离pgvector 的 <=> 返回的，越接近 0 越像。别跟相似度搞反。
全文检索按字面命中找。Ctrl+F 的进化版。
分词中文没空格，得先把句子切成词。「报销上限多少」→ 报销/上限/多少。
tsvectorPostgreSQL 把一段话拆成「词 + 位置」后存成的结构，就是这份词表索引。
tsquery你的查询拆成的「词条件」。
ts_rank_cdPostgreSQL 的全文打分函数。归一化后恒小于 1，输出量级很低。
归一化 32ts_rank_cd(...,32) 里的 32 是开关，含义是 rank/(rank+1)。别再说「无上界」。
BM25全文打分的一种经典公式。MaxKB 没用它，用的是 ts_rank_cd，面试说「全文打分」最安全。
混合检索 hybrid两路都跑，再把结果合并。
召回 recall先把「可能相关」的一大堆捞上来。海选。
候选池被捞上来的那批。池子外面的人再优秀也没机会。
Top-K取前 K 名。只录前 5 名。
命中率 hit@524 道题里，答案所在那篇进了前 5 的有几道。
名次 rank排第几。
RRF只看名次、不看分数地合并多路。Σ 1/(60+rank)。两个面试官打分标准不同，那就别比分，只比他把谁排前面。
k = 60RRF 分母里那个大数，压低头部霸权，防止某一路一家之言压倒一切。
融合粒度按段落投票还是按文档投票。按段落投，长文档段多就等于票多，不公平。
去重同一篇 / 同一段出现多次只算一次。一个人不能投三票。
阈值 threshold低于这个分就不给答案。这里取余弦 0.5。
拒答查不到就说查不到，别硬编。
Reranker 精排捞上来之后再用更贵的模型重排一遍。本项目没做。
Docker把软件和依赖打包成一个箱子跑。船不用管里面装什么。
镜像 / 容器镜像 = 设计图；容器 = 按图跑起来的那只箱子。
bind mount把本机目录挂进容器。改代码后容器重建不丢，全靠它。
SQL / CTEWITH … AS (…) 是先算一个临时结果再拿它继续查。先炒好配菜再下锅。
占位符 %sSQL 里留的坑，等程序填值。坑的数量必须和填的数一样多，多一个就报错。
API / Bearer程序之间递材料的窗口。Bearer token 是工牌，进门要刷，不能报名字。

1260 秒完整讲述（背下来，面试第一问就用）

这个项目基于 MaxKB 做文档知识库问答，我改的是检索层。
它的混合检索先把候选池砍到向量 Top-500，再在池子里把余弦相似度和全文分相加。
这有两个问题：一是纯字面命中（编号、型号）根本进不了池子；
二是两项分数量级差一个档，相加基本等于只看向量。

我做了两件事：两路各自独立召回；用 RRF 按名次融合，
在文档维度取每篇的最好名次再合并。

评测是我自己标的 24 道题加 8 道域外题。原版混合检索文档级 Top-5 是 54.2%，
改完是 83.3%，而纯向量和纯全文各只有 50%。

我也试过直接把 RRF 写进那条 SQL，结果段落级只有 50%、按文档聚合只有 37.5%，
比原版还低——所以瓶颈在候选池和融合粒度，不在公式。域外 8 题拒答 7 题。

三句不能说

① 准确率 90%   ② 线上 QPS   ③ 我改造了 MaxKB 源码（改说「复现它的检索逻辑做对照」）

13自检题（答不上就回去重读）

1. 为什么需要 RAG，而不是微调？
微调把文档烧进权重：贵、慢、文档一改就得重训，还容易把模型教傻。RAG 文档不动、回答时现场查，便宜、随时能改、能给出处。而且 RAG 给了「检索」这个可量化、可优化的环节——正是我做的部分。
2. 一段话为什么会有 3 条向量记录？带来什么坑？
MaxKB 给每段自动生成几个「关联问题」，正文一条 + 问题各一条。坑是同一段会占多个名次，融合时必须按段落去重，否则一段话能把 Top-5 占满。
3. 向量检索在什么地方一定瞎？举一个你标注集里的例子。
编号、型号、错误码、函数名这类「字面才有意义」的东西。EE-203 在向量空间里被平均成一团模糊。标注集里「打招呼第一句话怎么写」：向量排第 12，全文排第 3。
4. 原版 SQL 里 LIMIT LEAST(%s*10, 500) 为什么是病根？
候选池完全由向量一路决定。字面命中但语义不像的段落根本进不了池，关键词分加不上去——召回上限被另一路锁死。旁证：池子 50→500，命中率反而 75%→41.7%，说明瓶颈不是容量而是「由谁决定池子」。
5. ts_rank_cd(..., 32) 里的 32 是什么？取值范围多少？
归一化开关，输出 = rank/(rank+1)，恒小于 1。所以「全文分无上界」是错的。真实问题是它和余弦差一个量级：余弦普遍 0.8+，全文分多在 0.1 以下，相加等于只看向量。
6. 手算：A（向量 3 / 全文 7）和 B（向量 1 / 未命中），谁在前？
A = 1/63 + 1/67 = 0.0308；B = 1/61 = 0.0164。A 在前。因为 A 被两路同时认可，这就是 RRF 的投票效果。
7. 为什么按段落融合会输给按文档融合？
一篇长文档切出 30 段，全在前 20 名里就等于投了 30 票，融合被「这篇有多少段」带偏。按文档取每篇的最好名次才公平。实测：段落级 50.0%，文档级 83.3%。
8. 「文档级 Top-5 = 83.3%」里「文档级」和「top-20」各约束了什么？
文档级 = 按文档名去重后取前 5 篇，答案文件在这 5 篇里就算命中（不是段落级）。top-20 = 每一路只取前 20 条进融合，是融合协议的一部分，不是全量数据。换成段落级或换取数，数字都会变。
9. 池子从 50 放到 500，命中率为什么反而掉？
因为排序被向量项支配，池子越大越退化成纯向量排序（纯向量本库 50%），而全文那点加分被稀释。实测 blend 池 50 = 75%，池 500 = 41.7%。更细的消融我没做——这句可以老实承认。
10. 面试官说「你这是不是调参调出来的」，拿哪三行数据回他？
① RRF 两路各取 Top-10 仍有 75.0%；② 原版 blend 在池 50 时也有 75.0%（说明基数本身就有这么高）；③ k 取 20/60/100 差异在 ±1.5 个点内。参数不敏感，提升来自「候选池独立 + 文档级融合」这两个结构性改动。
